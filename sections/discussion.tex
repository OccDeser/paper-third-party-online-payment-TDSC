%-------------------------------------------------------------------------------
\subsection{Discussion}
%-------------------------------------------------------------------------------

\textbf{Advantages.}
SCC offers four advantages over existing payment patterns and over the two-phase design.
\begin{enumerate}[leftmargin=*]
  \item \textbf{Protection from the first payment.}
  Every payment, including the first payment to a merchant, binds the user's authorization to the order that the user's own checkout produced.
  \item \textbf{Single round and no per-user state.}
  Merchants store no per-user keys and \emph{PS-App} stores no bindings, so changing devices or reinstalling the payment application has no effect on security.
  \item \textbf{Small integration change.}
  Merchants add the fulfilment target to the signed order; the payment SDK handles the seal and the code.
  \item \textbf{Verification under the strongest channel assumption.}
  All five security properties hold when both external channels are insecure.
\end{enumerate}

\textbf{Costs and Scope.}
SCC adds one user action per payment and relies on three deployment conditions.
\begin{enumerate}[leftmargin=*]
  \item \textbf{User interaction.}
  The user enters a short code together with the payment password.
  In QR code payment, the code on the merchant page and the cashier on the phone are visible side by side.
  In in-app and mobile web payment, the user carries the code across the switch from \emph{MF} to \emph{PS-App}, and \emph{MF} keeps displaying it until the payment ends.
  \item \textbf{Code confidentiality on the device.}
  The security argument requires that the attacker not learn the code before the user enters it, which the secure channel between the user and \emph{MF} provides in our model.
  Malware that reads the screen or overlays a fake input page acts on the user's device and lies outside the channel attacker.
  \emph{MF} and \emph{PS-App} therefore render the code and its input field with screen-capture protection, such as \texttt{FLAG\_SECURE} on Android.
  \item \textbf{Coverage of the fulfilment target.}
  $D$ includes every order field that determines delivery, such as the shipping address, the recipient of a gift, a top-up number, or a game account.
  \emph{PS} enforces this by requiring merchants to declare these fields when they integrate SCC.
\end{enumerate}
The symbolic model treats the code check as exact; the code length bounds the probability of online guessing, as discussed in the security analysis.
Tampering with $D$ or with the seal makes a payment fail, and such denial of service lies outside our threat model.
