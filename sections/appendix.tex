\section{Payment Scenarios Illustrations}

Three third-party online payment scenarios were discussed in Section~\ref{sec:payment-scenarios}.
We provide detailed workflow diagrams for each of these payment scenarios, as shown in Figures~\ref{fig:inapp_payment}--\ref{fig:qr_code_payment}.

In in-app payment, as shown in Figure~\ref{fig:inapp_payment}, the workflow is as follows:

\begin{enumerate}[leftmargin=3.5em]
    \item[\textbf{Step 1}.] The user selects goods in the merchant application and initiates a purchase request.
    \item[\textbf{Step 2}.] The merchant application communicates with the merchant server to create the order and obtain the payment-relevant information required for the subsequent payment process.
    \item[\textbf{Step 3}.] The merchant application invokes the payment provider's SDK to launch \emph{PS-App} and delivers the payment information to \emph{PS-App}.
    \item[\textbf{Step 4}.] The user authorizes the payment within \emph{PS-App} by entering the payment password.
    \item[\textbf{Step 5}.] \emph{PS-App} submits the payment request to \emph{PS-Server}, which validates the request and proceeds with payment execution.
    \item[\textbf{Step 6}.] The \emph{PS-Server} performs the funds transfer to complete the transaction.
    \item[\textbf{Step 7}.] The \emph{PS-Server} sends a callback notification to the merchant server, enabling the merchant server to update the order status accordingly.
\end{enumerate}

    % add words
In mobile web payment, as shown in Figure~\ref{fig:mobile_web_payment}, the workflow is mostly similar to that of in-app payment.
The main difference lies in \textbf{Step 3}: the mobile web page launches \emph{PS-App} via a dedicated URL scheme registered by \emph{PS-App} at the operating system level.

In QR code payment, as shown in Fig.~\ref{fig:qr_code_payment}, the workflow differs from the previous two scenarios mainly in \textbf{Steps 1--3}, which are described below.
The remaining steps follow the in-app payment workflow.
\begin{enumerate}[leftmargin=3.5em]
    \item[\textbf{Step 1}.] The user selects goods in the merchant webpage and initiates a purchase request.
    \item[\textbf{Step 2}.] The merchant webpage communicates with the merchant server to create the order and obtain the payment-relevant information required for the subsequent payment process.
    \item[\textbf{Step 3}.] The merchant webpage displays a QR code encoding the payment information. The user scans the QR code on the mobile device, which launches \emph{PS-App} and transfers the payment information to \emph{PS-App}.
\end{enumerate}

\section{Alipay \& PSP-B Protocols}

We examined the actual protocol workflows of Alipay and PSP-B across three payment scenarios and documented them in detailed diagrams. 
Due to space constraints, we present a condensed version here.
The full versions are available in the open-source repository~\cite{third_payment_model_2026}.

Across the protocol diagrams, the involved entities include the user (\emph{U}), the merchant application (\emph{MA}), the merchant server (\emph{MS}), the merchant mobile web (\emph{MW}), and the merchant PC web (\emph{PW}). 

For Alipay, as shown in Figure~\ref{fig:alipay_payment_methods}, we explicitly distinguish the payment-side components as the Alipay payment application (\emph{APA}) and the Alipay payment server (\emph{APS}).

For PSP-B, as shown in Figure~\ref{fig:wechat_pay_payment_methods}, we denote the payment-side component as the PSP-B system (\emph{BPS}). In our diagrams, \emph{BPS} abstracts the payment-side functionality that is externally visible to the merchant and the user across scenarios.
