\section{Background}
%-------------------------------------------------------------------------------

In this section, we first introduce the typical ecosystem architecture and payment scenarios of third-party online payments. 
Then, we abstract two main high-level payment models, and finally introduce \Tamarin~\cite{Meier2013TAMARINProver}.

\subsection{Third-Party Online Payment Ecosystem} \label{sec:payment-ecosystem}

Currentlly, there is no universally adopted regulatory standard governing third-party online payments, 
and payment providers typically rely on proprietary protocols and implementations.
By reviewing official documentation and developer guides~\cite{WeChat2025APIV3,Alipay2025OpenPlatform}, alongside an analysis of payment workflows,
we summarize the typical ecosystem architecture of third-party online payment systems.
A typical third-party online payment ecosystem involves four main participants:

\begin{figure}[t]
    \centering
    \includegraphics[width=\linewidth]{img/tpp_process.pdf}
    \caption{
        An Overview of a Typical Third-Party Online Payment. 
        Dashed arrows indicate optional messages, depending on the specific payment model.
        Notation: $validate(p)$ denotes checking whether $p$ is valid; $continue()$ denotes continuing the execution of the protocol; $abort()$ denotes terminating the protocol; $make\_payment()$ denotes the fund transfer operation; $random()$ denotes generating a random number; and $sign_k(m)$ denotes signing message $m$ with key $k$.
    }
    \label{fig:third_party_payment}
\end{figure}

\begin{enumerate}[leftmargin=*]
  \item \textit{\textbf{User (U):}}
    % An individual who initiates a payment for goods or services.
    An individual who initiates and authorizes payments for goods or services.
  \item \textit{\textbf{Merchant Frontend (MF):}}
    The interface through which the user interacts to select goods and initiate the payment,
    typically implemented as a website or mobile application.
  \item \textit{\textbf{Merchant Server (MS):}}
    The server-side component of the merchant that processes orders and communicates with the payment provider.
  \item \textit{\textbf{Third-Party Payment System (PS):}}
    We refer to a payment transaction handling system provided by a payment service provider as \emph{PS}.
    The \emph{PS} consists of a payment application (\emph{PS-App}) and a payment server (\emph{PS-Server}).
    Since the internal interaction mechanisms are proprietary and the communication occurs over private secure channels, the two components cannot be individually inspected.
    Thus, we treat the \emph{PS} as a unified black-box system.
\end{enumerate}

As illustrated in Figure~\ref{fig:third_party_payment}, a third-party payment process can be abstracted into the following phases:
\begin{enumerate}[leftmargin=*]
  \item[\rom{1}.] \textit{\textbf{Order Phase:}}
    \emph{U} purchases $goods$ and selects a payment provider on \emph{MF}. 
    The \emph{MF} sends the $goods$ and payment provider to \emph{MS}.
  \item[\rom{2}.] \textit{\textbf{Prepayment Phase:}} 
    Based on the received information, \emph{MS} generates the corresponding payment parameters $params$ and returns them to \emph{MF}. 
    \emph{MF} forwards $params$ to the corresponding \emph{PS}.
  \item[\rom{3}.] \textbf{Authorization Phase:} 
    The \emph{PS} presents the order information (including product description, payment amount, and payee's account) to \emph{U} on the payment interface for confirmation. 
    After verifying the order details, \emph{U} enters the payment $password$ on the \emph{PS-App} to authorize and complete the transaction.
  \item[\rom{4}.] \textit{\textbf{Notification Phase:}}  
    After the authorization phase, \emph{PS-Server} signs the payment result using its private key and sends the signed result to \emph{MS}.
    Meanwhile, the \emph{PS-App} also shows the payment result page to \emph{U}.
\end{enumerate}
    
\subsection{Payment Scenarios}

\emph{PS-Server} obtains payment information from \emph{MF} via \emph{PS-App} on the \emph{U}'s mobile device.
However, the communication methods between \emph{PS-App} and \emph{MF} differ depending on how \emph{MF} is implemented, 
including native mobile applications, mobile web pages, and desktop web pages.
These distinct forms result in different payment scenarios, and payment providers accordingly define specific interaction methods between the \emph{MF} and the payment system (\emph{PS}).
In the following, we introduce three common payment scenarios:

\textbf{In-app Payment.}
This payment scenario takes place within native mobile applications.
After the user selects a product, the merchant application invokes the \emph{PS-App} through the Software Development Kit (SDK) provided by the payment provider,
transmits the required payment parameters, and subsequently completes the payment workflow.

\textbf{Mobile Web Payment.}
In mobile web payment, the user interacts with the merchant through a mobile browser rather than a native application.
Similar to in-app payment, the merchant's mobile web page initiates a payment request to the \emph{PS-App} using a URL scheme.

\textbf{QR Code Payment.}
QR code payment differs fundamentally from the previous two scenarios in terms of device interaction.
In this case, the user browses the merchant's website using a desktop browser, while the payment is executed on a mobile device.
Since a merchant's web page cannot directly redirect to a mobile payment application, the payment provider employs a QR code as an intermediary mechanism between the PC and mobile platforms. 
After a user places an order, the merchant website generates a payment QR code, which is scanned by the \emph{PS-App} to obtain the payment parameters and complete the transaction.
 
\subsection{Payment Models}\label{sec:payment-models}

As discussed earlier, during the \emph{Prepayment} phase, protocol designs vary across different providers and scenarios.
Here, we introduce two high-level payment models adopted by the two mainstream payment providers, WeChat Pay and Alipay.

\end{figure}

\begin{figure}[t]

  \caption{Payment Model B}
  \label{fig:payment_model_b}
\end{figure}

\textbf{Payment Model A.}
In this model, the payment parameters are generated by \emph{MS}.
Figure.~\ref{fig:payment_model_a} illustrates in detail the process by which \emph{MS} generates the order information.
Based on the $goods$ selected by the user, \emph{MS} calculates the payable $amount$ and the order $description$, and generates a unique order identifier~($id_{order}$). 
These values, together with the merchant identifier~($id_{M}$), constitute the order information.
\emph{MS} then signs the order information using its private key $Sk_{M}$, producing a signature value $sign_{order}$.
The order information and $sign_{order}$ are directly used as the payment parameters $params$.
During the subsequent \emph{Authorization} phase, \emph{PS} verifies $sign_{order}$ to confirm the integrity of the order information.
Payment Model A is adopted by Alipay in the In-app and Mobile Web Payment scenarios.

\textbf{Payment Model B.}
In Model~B, the payment parameters are generated with the involvement of \emph{PS}.
Similarly, \emph{MS} is required to sign the critical order information.
However, unlike Model~A, the order information and its signature $sign_{order}$ cannot be directly used as payment parameters.
Instead, they are sent to \emph{PS} as a prepayment request.
After verifying $sign_{order}$, \emph{PS} generates a unique prepayment identifier~($id_{prepay}$) for the payment and returns it to \emph{MS}.
\emph{MS} then concatenates $id_{M}$ with $id_{prepay}$ and signs the result again using $Sk_{M}$, producing a new signature $sign_{prepay}$.
Finally, $id_{M}$, $id_{prepay}$ and $sign_{prepay}$ are sent to \emph{PS} as the payment parameters $params$ in subsequent phases.
\emph{PS} verifies the validity of $sign_{prepay}$ to ensure the integrity of the payment request.
Payment Model~B is adopted by Alipay in the QR Code Payment scenario and by WeChat Pay across all three payment scenarios.


\subsection{\Tamarin}

\Tamarin is a symbolic verification framework widely used for analyzing real-world security protocols, 
including EMV~\cite{Radu2022EMVRelayProtection,Basin2021EMVStandard,Basin2021CardBrandMixup}, TLS~\cite{Cremers2016AutomatedTLS,Cremers2017ComprehensiveTLS,Lee2019maTLS}, Bluetooth~\cite{Shi2023FormalBLEPairing,Jangid2023ExtrapolatingBluetoothPasskey,Shi2026FormalBLESC}, and 5G-AKA~\cite{basin2018formal,cremers2019component}.
It employs a multiset rewriting system to model protocol execution and adversary capabilities, providing a rich language for specifying security properties as first-order logic formulas over execution traces. 
\Tamarin supports unbounded protocol sessions, a Dolev-Yao style adversary, and is particularly suited for analyzing stateful protocols due to its native handling of mutable and persistent state.

\textbf{Terms and Facts.}
In \Tamarin, protocol messages are represented as \emph{terms}, which are built from variables, constants, and compound expressions formed by applying function symbols $f \in \Sigma$ to subterms.
An equational theory over terms defines their algebraic properties and reducibility relations, thereby affecting pattern matching and substitution.
For example, symmetric encryption is modeled by the equation $\text{\Tfunction{sdec}}(\text{\Tfunction{senc}}(m,k),k)=m$.
The system state is captured using \emph{facts}, which are atomic predicates of the form \TFactTerm{F}{$t_1,\ldots,t_n$} that represent resources or observable events.
Facts can be linear (consumed upon rule application), persistent (available throughout the execution, e.g., \TFactTerm{!PK}{$A,Pk_A$}), or action facts, which record execution steps such as \TFactTerm{Running}{$A,x$} and \TFactTerm{Commit}{$B,x$} and are retained to form execution traces but do not constitute mutable state.


\textbf{Multiset Rewriting Rules.}
Multiset rewriting rules provide a description of protocol behavior.
A rule specifies a state transition by means of \emph{left-hand side} premise facts (guards) and \emph{right-hand side} conclusion facts (productions), and may carry action facts as observable events.
Formally, a rule can be written as 
\begin{tightflalign}
  \TFacts{  LF_1,\ldots,LF_m } \TEmpActFactSL{AF(t_1, \ldots, t_k)} \TFacts{  RF_1, \ldots, RF_n } &
\end{tightflalign}
Given the current state multiset $S$, the rule is enabled when $LF_1,\ldots,LF_m \subseteq S$
Its application yields a new state $S' = (S \setminus \{LF_1,\ldots,LF_m\}) \cup \{RF_1, \ldots, RF_n\}$,
and records the action fact $AF(t_1, \ldots, t_k)$ in the execution trace.

\textbf{Trace and Formulas.}
In \Tamarin, the global behavior of a protocol is characterized by traces, which are sequences of action facts generated by rule applications, 
formally written as $\tau = \langle FA_1@t_1, FA_2@t_2, \dots, FA_n@t_n \rangle$, where $FA_i@t_i$ denotes an observable event occurring at time point $t_i$.
Based on traces, \Tamarin reasons about executions using first-order logic formulas, where \emph{restrictions} are used to specify global constraints over all possible executions.
These constraints are predicate formulas over events and time points.
Within this restricted semantic space, security properties are likewise expressed as first-order temporal logic formulas (lemmas), such as secrecy, authentication, or consistency properties, and are required to hold for all valid traces.
For example, key secrecy can be formalized as:
\begin{tightflalign}
    \TAll \;\text{\Tterm{k \#i.}} \;\text{\TFact{Install(k)@\#i}} \implies \TNot (\TEx \;\, \text{\TLemma{\#j.}} \;\text{\TFact{K(k)@\#j}} ) 
\end{tightflalign}
This formula describes that for all time points~$i$, if a key~$k$ is installed at time~$i$, then there doesn't exist a time point~$j$ at which the key~$k$ is known by an adversary.
