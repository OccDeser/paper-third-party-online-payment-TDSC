In this section, we analyze the causes of order tampering attacks and introduce our countermeasure.
Then, we present the symbolic verification results of our countermeasure and discuss its advantages and limitations.

\subsection{Cause Analysis}

\textbf{Superficial Causes}
From a superficial perspective, order tampering attacks arise from the existence of insecure communication channels between \emph{MS} and \emph{PS-App}.
An attacker can intercept and tamper with order information along this channel, thereby misleading the user into authorizing an incorrect payment.
At first glance, addressing this issue appears straightforward.
It suffices to ensure that the communication channels between \emph{MS} and \emph{PS-App} are secure.
However, for payment service providers, this seemingly simple solution is difficult to realize in practice.
The security of the communication path from merchant backends to \emph{PS-App} is influenced by both merchants and end users, and is largely beyond the control of payment service providers.
Payment service providers serve a large number of merchants, each with diverse backend implementations, making it infeasible to ensure that all merchants correctly secure their communication channels.
Similarly, merchants serve a vast user base with heterogeneous device environments, and payment service providers cannot guarantee that all users operate within secure network conditions.
Therefore, defending against order tampering attacks solely by securing communication channels is, in practice, highly challenging.
Consequently, mitigation is often reactive: once an insecure communication channel is identified, merchants and users are notified to apply patches.

\textbf{Root Causes}
The root cause of such attacks lies in the lack of an effective user-side authentication mechanism for order information in existing payment models.
We examine the typical actions performed by users during the payment process: entering a payment password to authorize the transaction, and possibly verifying the payment amount and description.
However, the user does not actually authenticate the order itself.
Information such as the payment amount and item description merely represents the content of the current payment, and does not correspond to the original order that the user intends to confirm.
In other words, during the \emph{Authentication} phase, the user performs no form of authentication of the order data.
The user's authorization is applied only to the act of payment transaction, rather than to a specific order.
Once an attacker is able to tamper with order parameters in transit, the user can be induced to authorize an incorrect order.
This observation reveals a fundamental design flaw in current payment models.

To fundamentally address order tampering attacks, we design and propose a new third-party payment model that introduces a user-side order authentication mechanism to effectively prevent such attacks.
Our payment model distinguishes between \emph{initial} and \emph{regular} payments, whose workflows are illustrated in Fig.~\ref{fig:our_model_initial} and Fig.~\ref{fig:our_model_regular}, respectively.
For a given merchant and user, the first payment initiated by the user is defined as an \emph{initial} payment, while all later payments are defined as \emph{regular} payments.
Our model is backward compatible with existing payment models, preserves most of their workflows, and enables payment service providers to deploy it incrementally without modifying the existing payment process.

At the beginning of the \emph{Prepayment} phase of a user's initial payment, \emph{MS} generates a public–private key pair $(priv_{UA}, pub_{UA})$ for \emph{U}, and then uses the merchant private key $priv_M$ to sign $pub_{UA}$ together with the order information before sending them to \emph{PS}.
Then, \emph{PS} temporarily stores $pub_{UA}$ together with the order information and returns the prepay identifier~($id_{prepay}$) to the merchant.
Upon receiving $id_{prepay}$, \emph{MS} generates two signatures over the payment parameters using $pub_M$ and $pub_{UA}$, respectively, and sends signatures and $id_{prepay}$ to \emph{MF}
During the \emph{Authentication} phase, \emph{PS-Server} send the order information together with $pub_{UA}$ to \emph{PS-App}.
At this point, \emph{PS-App} notifies the user that this is the first payment to the merchant and asks whether this merchant should be trusted.
If the user chooses to trust the merchant, \emph{PS-App} verifies both signatures and, upon successful verification, binds $pub_{UA}$ to the merchant identifier and stores it locally;.
Otherwise, the payment process is aborted.

In regular payments, the \emph{Prepayment} phase largely follows Payment Model~B.
The only difference is that \emph{MS} additionally signs $id_{prepay}$ and $id_{M}$ using $priv_{UA}$.
Then, \emph{PS-App} first checks whether a public key $pub_{UA}$ has already been bound locally to the merchant identifier.
If such a binding exists, \emph{PS-App} verifies both signatures before prompting the user to confirm the order information and complete the payment.
Otherwise, the application informs the user that the merchant is not trusted and asks whether to proceed with the payment.

The analysis shows that under all three channel assumptions, our regular payment model effectively defends against order tampering attacks and satisfies all security properties.
This demonstrates that by introducing an order authentication mechanism on the user side, we can fundamentally address the problem of order tampering attacks.
Although our initial payment model does not satisfy all security properties under certain channel assumptions, which is consistent with the behavior of Model~B,
