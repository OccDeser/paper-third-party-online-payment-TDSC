In this section, we analyze the causes of order tampering attacks, introduce our countermeasure, verify it using symbolic methods, and discuss it.

\subsection{Cause Analysis}

\textbf{Superficial Causes.}
From a superficial perspective, order tampering attacks arise from insecure communication channels between \emph{MS} and \emph{PS-App}, over which an attacker can tamper with order information and mislead the user into authorizing an incorrect payment.
Securing these channels is difficult for payment service providers in practice: the path from merchant backends to \emph{PS-App} depends on the backend implementations of a large number of merchants and on the network environments of a vast user base, both of which lie beyond the providers' control.
Consequently, mitigation is often reactive: once an insecure communication channel is identified, merchants and users are notified to apply patches.

\textbf{Root Causes.}
The root cause of such attacks lies in the lack of a user-side authentication mechanism for order information in existing payment patterns.
During payment, the user enters a payment password to authorize the transaction and possibly checks the payment amount and description.
These values describe the content of the current payment, not the original order that the user intends to confirm, so the user's authorization applies only to the act of payment rather than to a specific order.
Once an attacker is able to tamper with order parameters in transit, the user can be induced to authorize an incorrect order.

An order created through the order oracle carries the same amount, description, and payee as the user's order, so it passes every check the user performs; the two orders differ only in the order instance and in the account that placed it.
\emph{PS} cannot tell them apart either, because it cannot authenticate the sender of the payment parameters, so a countermeasure has to give \emph{PS} a check, carried by the user, that the attacker cannot reproduce with its own order.

\subsection{Design Goals}

A countermeasure against order tampering should meet three goals.
\begin{enumerate}[leftmargin=*, label=\textbf{G\arabic*}]
  \item \textbf{Security under weak channel assumptions.} The protocol satisfies all security properties of Section~\ref{sec:security_properties} when both \emph{MF} $\Longleftrightarrow$ \emph{MS} and \emph{MF} $\Longleftrightarrow$ \emph{PS} are insecure, without requiring the user to recognize the payee account.
  \item \textbf{No per-user state.} Each payment completes in one protocol run without long-term keys or bindings for individual users, so the first payment to a merchant is protected like any other.
  \item \textbf{Small changes for merchants.} Merchants keep the existing message flow and notification interface; the signed order gains one field, the user account.
\end{enumerate}
Our countermeasure, Sealed Checkout Code (SCC), meets all three goals.

\subsection{Countermeasure Design}

SCC uses the user as the link between \emph{MF} and \emph{PS} that the attacker does not control.
For each payment, \emph{MF} draws a fresh nonce $r$, seals it to \emph{PS} together with a digest of the order handle and the user's account, and shows a short code derived from $r$ to the user.
\emph{PS} accepts the seal only for the order it was created for, and completes the payment only if the user enters the same code.
Fig.~\ref{fig:cm_scc} shows the workflow on top of payment pattern~B.

\textbf{User account.}
$id_{U}$ denotes the account under which the user is logged in at the merchant.
\emph{MF} knows $id_{U}$ from the user's login, and \emph{MS} associates each order with the account of the logged-in user.
As in the rest of the paper, the user's login session with \emph{MS} is authentic, and the attacker controls the payment messages on the two external channels.
An attacker places orders on accounts it controls, so every order created through the order oracle carries an account other than $id_{U}$.

\textbf{Order Phase.}
The user selects $goods$ in \emph{MF}, and \emph{MF} sends $goods$ to \emph{MS} within the user's login session, which identifies $id_{U}$.

\textbf{Prepayment Phase.}
\emph{MS} includes $id_{U}$ in the order it signs and submits to \emph{PS}, and \emph{PS} records the order under a fresh $id_{prepay}$.
\emph{MS} then generates the payment parameters exactly as in pattern~B.
Upon receiving the parameters, \emph{MF} draws $r$, computes $code = f(r)$ and $T = H(id_{M} \parallel id_{prepay} \parallel id_{U})$ with its own $id_{U}$, and encrypts $T \parallel r$ under the public key $pub_{P}$ of \emph{PS} to obtain $seal$.
\emph{MF} displays $code$ to the user and sends the payment parameters together with $seal$ to \emph{PS}.
\emph{PS} verifies $S_{prepay}$, looks up the order recorded for $id_{prepay}$, recomputes $T'$ from the merchant identifier, the order handle, and the user account in that order, and decrypts $seal$.
It continues only if $T = T'$.

\textbf{Authorization Phase.}
\emph{PS-App} displays the amount, the description, and the payee account, and asks the user to enter the code.
The user enters the code shown by \emph{MF} together with the payment password, and \emph{PS} completes the payment only if the code equals $f(r)$ and the password is valid.

\textbf{Notification Phase.}
This phase is identical to pattern~B.

\textbf{Direction of the code.}
\emph{PS} never displays the code.
Payment parameters are bearer tokens: any party holding them can open the cashier.
If \emph{PS-App} displayed the code for the user to compare, an attacker that intercepts the parameters and the seal could open the cashier under its own payment account, read the code, and choose a nonce $r_A$ with $f(r_A)$ equal to that code for its own order.
In SCC the code travels only from \emph{MF} to the user and from the user to \emph{PS}, both over secure channels.

\textbf{Integration.}
Merchants integrate SCC by adding $id_{U}$ to the signed order.
The seal and the code are computed by the payment SDK embedded in \emph{MF}, which also carries $pub_{P}$; the message flow and the notification interface remain unchanged.

\subsection{Security Analysis}

The attacker controls \emph{MF} $\Longleftrightarrow$ \emph{MS} and \emph{MF} $\Longleftrightarrow$ \emph{PS} and obtains legitimate payment parameters for its own orders through the order oracle.
To make the user pay for an order of its own, the attacker has two options.

\begin{enumerate}[leftmargin=*]
  \item \textbf{Substitute its own order.}
  The attacker replaces the user's payment parameters with those of its own order, either on \emph{MF} $\Longleftrightarrow$ \emph{MS} (Variant~\Rom{1}) or on \emph{MF} $\Longleftrightarrow$ \emph{PS} while keeping the user's seal (Variant~\Rom{2}).
  In Variant~\Rom{1}, \emph{MF} seals the attacker's order handle together with the user's $id_{U}$; in Variant~\Rom{2}, the seal carries the user's order handle.
  \emph{PS} recomputes $T'$ from the attacker's order, which carries the attacker's own handle and account, so $T \neq T'$ and \emph{PS} aborts.
  \item \textbf{Forge a seal for its own order.}
  The attacker builds a consistent seal for its own order with a nonce $r_A$ of its choice.
  \emph{PS} opens the cashier, but the payment requires $f(r_A)$, while the user enters the code $f(r)$ shown by its own \emph{MF}.
  The nonce $r$ appears only inside the seal, and $f(r)$ only on the user's channels to \emph{MF} and \emph{PS}, so the attacker can only guess.
  With a four-digit code, a guess succeeds with probability $10^{-4}$.
\end{enumerate}

Except for guessing the code, the attack ends with a failed payment and does not redirect the user's funds or goods.

\subsection{Symbolic Verification}

We model SCC in \Tamarin following the models of Section~\ref{sec:modeling}, with the same channel rules, tactics, and lemmas.
The model uses the Base assumption, in which both \emph{MF} $\Longleftrightarrow$ \emph{MS} and \emph{MF} $\Longleftrightarrow$ \emph{PS} are insecure; every trace admitted under SecureMS or SecurePS is also admitted under Base, so the results carry over to both.
Through the order oracle, the attacker places orders with arbitrary amounts and descriptions on any account other than the honest user's, and \emph{MS} signs that account into each order.
The model has one honest user and no payment account for the attacker, so the argument for the direction of the code lies outside the model.

The user commits to the order when the payment completes, because \emph{PS} checks the code after the user submits it.
To confirm that this commit point preserves the discriminating power of IA-O2, we applied the same change to all six protocols of Table~\ref{tab:lemma-results} under all three channel assumptions; IA-O2 remains falsified in all 18 models.

Table~\ref{tab:countermeasure-results} summarizes the results.
SCC satisfies all five security properties under the Base assumption, and an exists-trace lemma confirms that an honest payment completes in the model.
The verification used \Tamarin version~1.10.0 and Maude~3.4 on a server with a 16-core, 32-thread AMD Ryzen~9 7950X3D processor and 187~GB of memory (peak usage 5.3~GB).
